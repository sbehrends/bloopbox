# Box software review and improvement plan — 2026-09-23

A full review of `box/software/`: the two daemons, the root net agent, the four browser UIs,
packaging, CI and the tests. Seven areas were reviewed in parallel, each by reading every file
in it, and then the highest-severity findings were re-verified by hand against the code
(marked **✔ verified**). Baseline at the time of review: `npm run check` green, 636 tests,
coverage **82.8 % statements / 73.3 % branches** (the docs still say 77/68).

This document is a plan, not a record. As items ship, move what is left into `PENDING.md` and
delete this file — `docs/` is for reasoning that stays true.

---

## Verdict

The engineering culture here is unusually good: decisions are written down with their reasons,
the pure core runs on fake timers, the IPC edge narrows `unknown` without casts, nothing uses
`shell: true`, the whitelist is fail-closed and checked before download, and the release is
byte-reproducible. **Keep all of that.**

The weaknesses are of three kinds, in order of urgency:

1. **Audio-path concurrency loses voice notes in ordinary use.** The single most common
   scenario — a second note arrives while the child is listening to the first — cuts the first
   note off, deletes it and sends a read receipt. Tests cannot see it because the mock HAL does
   not model interruption. This is the product's core promise failing silently.
2. **A handful of real security gaps on the LAN / open hotspot**: the child's recordings and
   the raw pairing QR are served without a password, body-less admin POSTs are CSRF-able, and CI
   bakes one ssh password into every published image and prints it in the job log.
3. **Rules enforced by prose instead of by the gate.** The typed IPC contract is not wired into
   a single Socket.io endpoint; the layer rules, the route auth list, the "four places" config
   rule and the decision→test links are all maintained by hand, and some have already drifted.
   Every runtime failure in `DeviceController` is swallowed without a log line, which will make
   first-hardware bring-up needlessly blind.

The structural direction below is **ports-and-adapters made explicit**, since the code is
already most of the way there: `core/` = domain, `hal/ net/ system/ stats/ config/` = driven
adapters, `server/` + `bridgeLink` = driving adapters. What is missing is a thin application
layer in the middle, and a gate that enforces the boundaries.

### 0.1 A cue during playback kills the note, which is then deleted and marked read — ✔ verified

- `deviceController.ts:234` plays `Notify` on arrival even while a queue is playing;
  `gpioDriver.ts:399-403` `playCue()` calls `stopPlayback()` first; `gpioDriver.ts:479`
  treats a signal exit as success; `queueManager.ts:136-137` pushes to `played` **regardless of
  `ok`**; `queueDrained` then deletes the file and sends the receipt. The whoosh/oops at the end
  of a send (`deviceController.ts:450,465,479,491`) do the same if the child is already
  listening.
- Second half: the killed `aplay`'s `close` handler sets `#playbackProcess = null`
  unconditionally, after the cue's `aplay` was spawned — so the next `stopPlayback()` kills
  nothing and the single-open `plughw` device returns "busy" for the next note, which is then
  also counted as played and deleted.
- **Fix**
  - One `#cue(cue)` method in the controller, the only caller of `hal.playCue`. It drops
    courtesy cues (notify, whoosh, oops) while `#listeningTo !== null` — the blinking lamp
    already carries the news.
  - `hal.play()` resolves `'completed' | 'interrupted'`; the queue adds to `played` only on
    `'completed'`; a failed play is **not** played.
  - `gpioDriver`: `if (this.#playbackProcess === child) this.#playbackProcess = null`, and
    `stopPlayback()` awaits the old child's `close` (SIGKILL after ~500 ms) before returning.
  - `MockHal.playCue` must interrupt playback the way the real driver does, and `types.ts`
    must say so — otherwise the controller tests stay blind to this class of bug.

### 0.2 Finishing a queue clears unread even when a note arrived mid-playback — ✔ verified

`deviceController.ts:378` `state.clearUnread(index)` zeroes the count while the new note sits in
the queue (`queueManager.ts:98` promises it "re-lights the LED"). Lamp goes dark, a tap beeps
"oops", the note is stranded until restart or the 48 h purge. **Fix:** `setUnread(index,
queue.count(index))` on drain and abort — better, derive unread from the queue so there is one
source of truth.

### 0.3 A stop during the inter-note chime still plays the next note in full

`queueManager.ts:115-139` checks abort only at the top of the loop. And on abort the notes
already played are neither deleted nor marked read, so the next restart (every config save)
restores heard notes as unread. **Fix:** re-check after the chime; change the event to
`playbackAborted { played, remaining }` and treat `played` like a drain.

### 0.4 The purge's "keep queued notes" set is a boot-time snapshot — ✔ verified

`hardware-server.ts:466,480` pass `controller.protectedFiles()` once. **Fix:** `keep: () =>
ReadonlySet<string>` read on each sweep. Decide in `PRODUCT.md` which wins at 48 h —
"deleted regardless" or "queued survives" — because the comment and the doc disagree.

### 0.5 Offline notes can be dropped at boot before the whitelist arrives

`whatsapp-bridge.ts:34,258`: the whitelist starts empty and is filled only by
`wa:contactsChanged`, but `client.start()` connects immediately and WhatsApp flushes the offline
backlog (`append`) right after open — already acked, never redelivered. Likely on every config
save, since the hardware server restarts and the socket.io client backs off up to 10 s.
**Fix:** hold voice-note events in a bounded buffer until the first contact list arrives, then
evaluate them. The whitelist still runs before download.

### 0.6 The child's recordings are downloadable without a password — ✔ verified

`hardware-server.ts:373` mounts `/audio` over `RECORDING_DIRECTORY` **and** `NOTES_DIRECTORY`
for every HAL driver; `captivePortal.ts:37` lets it through on the open hotspot; captures are
named `rec-<base36 counter>` from 1 on each boot. **Fix:** mount only when the simulator HAL is
active; add a harness test that the GPIO build answers 404.

### 0.7 The raw pairing QR is on an unauthenticated route — ✔ verified

`routes.ts:113-127` returns `qr` from open `GET /api/whatsapp`, while `/whatsapp/qr.svg` is
gated "because whoever scans it becomes the account". Anyone on the LAN can win the scan during
a re-pair. The panel only uses the string to detect rotation. **Fix:** return a short hash or a
counter; update the test that currently pins the leak.

### 0.8 The root agent probably cannot delete the request file — ✔ unit verified, runtime to confirm

`bloopbox-net.service` has `ProtectSystem=strict` and no `ReadWritePaths=/run/bloopbox`, so
`rm -f "${REQUEST_FILE}"` (`net-agent.sh:332`) fails silently and the action runs anyway —
every 5 s, forever, with the Wi-Fi passphrase left on disk (and then bundled by
`collect-diagnostics.sh:77`). Confirm on the device with
`systemd-run --wait -p ProtectSystem=strict touch /run/bloopbox/x`.
**Fix:** `ReadWritePaths=/run/bloopbox`; act **only if** the delete succeeded; open the file
with `O_NOFOLLOW|O_NONBLOCK` and check it is a regular file ≤ 4 KiB owned by `bloopbox` (a FIFO
there hangs root forever). On the daemon side `netState.ts:301` / `power.ts:50` must write
tmp + rename — today a read between truncate and write drops a reboot or join while the panel
reports success.

### 0.9 CI images share one ssh password and print it in the log — ✔ verified, **done 2026-09-23**

Shipped as described below, except the hotspot sshd deny, which was deliberately left out:
an image built with `--password` is how the hotspot flow itself gets debugged. The factory
reset not rotating the password is a follow-up in `PENDING.md`.

`build-sd-image.sh:307-313` generates one password per build (so per release asset, for every
device flashed from it) and `:463` echoes it into the job log. A `WIFI_PSK` secret would also
end up cleartext in a public image.

**Constraint:** the flash-and-go setup must not get harder, so ssh stays on and no key
management is asked of a parent. **Fix: generate the password per device on first boot and
show it in the admin panel.**
- The image's `userconf.txt` carries the hash of a throwaway random password that is never
  recorded, so nothing baked into the image can log in.
- A root oneshot ordered `After=userconfig.service` and `Before=ssh.service` runs when
  `/data/ssh-password` is missing: it generates a password from `/dev/urandom`, applies it
  with `chpasswd`, and writes it `0640 root:bloopbox`.
- The admin panel shows it under Advanced → SSH access, behind `requireAdmin`. Optionally,
  "regenerate" is one more enum action in the root agent's allowlist.
- Parent flow is unchanged: flash, boot, onboard. Whoever needs ssh reads the password from the
  panel they already have.

Independent of that: stop echoing it (`:463`); drop the `sd-card-credentials` artifact from CI,
since artifacts on a public repo can be downloaded by any signed-in GitHub user; refuse
`WIFI_PSK` in CI; and deny sshd on the hotspot interface (`10.42.0.0/24`), which today exposes
ssh to anyone in radio range during setup. `--ssh-pubkey FILE` stays as a developer option
for local builds.

### 0.10 The staged lockout diff: one lost up-edge now freezes every button

`buttonInterpreter.ts:232-235,440-442` (staged). Blocked, withheld and chord-swallowed presses
hold no timer, so only a button-up clears them — and with the new lockout that stuck press
blocks the **other** buttons indefinitely. `gpioDriver.ts` has never run on hardware and
debounce is in software, so a lost edge is plausible. **Fix before committing:** a watchdog on
every press (`maxRecordingMs + resumeGraceMs`) that drops it silently; later, read the line
level on each down-edge. Also tighten the new `listeningTo` tests to go through `setup()`, so
`toEqual([])` sees all ten events.

### 0.11 Portal recovery rejects passwords containing ä/ö/ü/ß — ✔ verified

`public/portal/main.ts:254` `btoa()` encodes Latin-1, `auth.ts:44` decodes UTF-8. A character
outside Latin-1 makes `btoa` throw outside the `try`, leaving the button stuck on
"Connecting…". **Fix:** `btoa(String.fromCharCode(...new TextEncoder().encode(s)))`, inside the
`try`.

### 0.12 Sender-chosen message ids become file paths; the server trusts IPC paths

`client.ts:461` / `recovery.ts:44` put `key.id` (set by the sender's client) into
`join(NOTES_DIR, …)`; `bridgeLink.ts:301-316` then plays and later `rm`s whatever path the
bridge reports. Any member of an assigned group qualifies. **Fix:** drop ids not matching
`/^[A-Za-z0-9_-]{1,128}$/`; on the server accept only `resolve(p)` inside `NOTES_DIR`
(respectively `RECORDING_DIR` for `wa:send`) with the expected name pattern.

**Core**
- Chord-unmute during quiet hours is undone within 15 min: `deviceState.ts:129` +
  `deviceController.ts:578` re-assert the schedule every tick. Act only on a schedule *edge*,
  or model `override: 'none'|'audible'|'silent'` cleared at the next boundary.
- A cancelled capture still opens the microphone after the bip (`deviceController.ts:419-425`),
  including on top of the oops and after `stop()`. Per-capture cancel token checked after the
  pop.
- `recordBlocked` gates the oops on `state.playing` (`:339`) while the lockout uses
  `#listeningTo`; use one signal. Add `dispose()` so `hal.on` listeners are removed.
- `quietHours.ts:99-112` ignores seconds (up to 59 s late); compute in ms.

**Server**
- CSRF / clickjacking: the panel relies on the browser's saved Basic credentials, so
  body-less POSTs (`/factory-reset`, `/whatsapp/unlink`, `/stats/reset`, `/silent`…) work from
  any website. One `/api` middleware for non-GET: reject `Sec-Fetch-Site: cross-site` or a
  foreign `Origin`, require `application/json`; send `X-Frame-Options: DENY`.
- bcryptjs (~300 ms on a Zero 2 W) on **every** admin request, on the event loop that times
  button presses — first suspect for the known "sluggish during pairing". Cache a successful
  check keyed on SHA-256(header ‖ stored hash) with a TTL; global failure backoff (429).
- Socket.io is attached only to `:3000` (`hardware-server.ts:155`); on `http://bloopbox.local/`
  the panel's live status never connects. `io.attach(portalServer)`. ✔ verified
- Shutdown (`hardware-server.ts:644-661`) is unbounded and one rejection skips the rest
  (LEDs stay lit, stats maybe unflushed). Arm the fallback timer first, wrap each step,
  register signal handlers at the top of `main`, add `unhandledRejection` /
  `uncaughtException` → `shutdown('fatal')` in **both** daemons.
- Request ids restart at 1 per boot (`events.ts:190`) while the bridge survives the restart:
  a stale `send-1` result can resolve the new `send-1`. Per-boot random prefix.

**WhatsApp**
- An unscanned QR loops forever: Baileys ends with 408 `timedOut`, treated as transient
  (`client.ts:386-407`). If `!isPaired(creds)` and the code is not 515, settle in `notLinked`.
  ✔ verified
- `unlink` / `beginLinking` / `#connect` race: timer not cleared on unlink; state set only after
  three awaits (one an unbounded `fetchLatestBaileysVersion`), so a double click opens two
  sockets writing the same `creds.json`. Set state synchronously, generation token checked after
  every await, end the old socket first.
- Reconnect ladder: counter resets on `open`, so 440 `connectionReplaced` (cloned card) loops
  every 2 s; 403 retried forever; no jitter. Reset only after 60 s up, treat 440/403 as
  terminal, ±20 % jitter.
- Voice notes inside `ephemeralMessage` (disappearing chats) are ignored (`client.ts:437`).
  Unwrap it explicitly; decide view-once as a product question. Do **not** adopt
  `normalizeMessageContent` wholesale — it widens what a group can deliver. ✔ verified
- "Delete for everyone" is not honoured: subscribe to `messages.update` REVOKE → new
  `wa:revoked` event (edit `events.ts` first) → remove from queue and disk.
- Downloads: no size cap, timeout or retry, onto the card that holds config and creds. Reject
  `fileLength` > ~2 MB, byte-counting transform, `AbortSignal.timeout(60 s)`, 2–3 retries.
  Write `*.part` → fsync → rename; recovery skips zero-length files.
- Send: pass `mediaUploadTimeoutMs` below the hardware side's 60 s, or the child hears "oops"
  for a note that was delivered. `void saveCreds()` → `.catch(log)`.

**HAL / audio / config**
- `durationMs` is wall-clock including grace and encode, so `MIN_USABLE_AUDIO_MS` never catches
  an empty microphone and stats are inflated ~15-20 %. Compute from WAV size.
- `prepare()` and `play()` can decode the same note concurrently into one file; keep a
  `Map<path, Promise>` of in-flight decodes. `release()` during a decode leaks the WAV.
- `arecord` exiting on its own is unobserved, so every commit waits the 2 s timeout.
- No timeout on any ffmpeg/amixer child; one wedged ffmpeg stops every later `prepare`. And
  `runQuiet` discards amixer stderr, which is why a wrong mixer name logs nothing.
  → one `runProcess({cmd,args,timeoutMs,stderrTail})` with SIGTERM→SIGKILL, used everywhere.
- Delete the unused `input?: Readable` path in `ffmpeg.ts:136-166` (unhandled EPIPE waiting to
  happen).
- Pause background decodes while capturing and `setPriority(pid, 10)` them — a loudnorm decode
  beside `arecord` risks xruns in the child's take.
- `configManager.ts:180-202`: fixed tmp name, no directory fsync, no save serialisation (two
  tabs lose an update). Unique tmp, promise mutex, fsync the directory, unlink tmp on failure.
  Same for `statsStore.ts`, whose overlapping `flush()` can let the process exit mid-write.

**Deploy**
- `wifi-apply.sh:103` still sets `key-mgmt none` (WEP) for open networks — they never connect.
- `wifi-apply.sh:111` `nmcli con up` without `--wait` blocks the hardware unit's
  `ExecStartPre` up to 90 s → dark buttons at boot. `--wait 10`.
- `net-agent.sh:409-417` escapes only `\` and `"`: a neighbour's SSID with a control character
  makes `net-state.json` unparseable → *unknown* → the hotspot never rises. A stranger's router
  name disables recovery. Emit with the bundled node's `JSON.stringify`.
- `Restart=always` + default `StartLimit` (5/10 s, config-save exits included) can leave the
  hardware unit `failed` until reboot. `StartLimitIntervalSec=0`, `RestartSteps`,
  `RestartMaxDelaySec`.
- No liveness: `Type=notify` + `WatchdogSec=30` with a periodic `WATCHDOG=1` from the event
  loop; `READY=1` after HAL init.
- `MemoryMax` (192 + 288 MB) exceeds what a 512 MB board has; set `OOMScoreAdjust` so the
  kernel kills the bridge before the hardware daemon.
- No RTC: quiet hours, purge TTL and debug deadline trust the wall clock. Publish
  `NTPSynchronized` in `net-state.json`; treat quiet hours as unknown until synced.
- Journald: pin `Storage=volatile` / `RuntimeMaxUse=16M` in normal mode, or a capped persistent
  journal — decide once (see Phase 2A).

## Phase 2 — architecture (M/L; do in this order, each PR green on its own)

### 2A. Observability first — it pays for everything after it — **done 2026-10-02**

**Done.** `onFault`, the routes logger and the fatal handlers (Phase 1); then, on
`software/fine-tuning-phase-2`: the warn/error ring on the health card (`GET /api/system/events`),
WhatsApp addresses masked in every log line the bridge writes and Baileys pinned to `warn`, a child
logger per subsystem, and the three-rule error policy in `architecture.md`.

**Not built: the `wa:heartbeat`.** On inspection both failures it was for are already detected.
Baileys ends a socket that has received nothing for `keepAliveIntervalMs + 5 s` (35 s) with
`connectionLost`, which reaches the hardware server as a status; and Socket.io pings the bridge
every 25 s and drops it after 20 s of silence, which the hardware server sees as the link going
down. A third heartbeat would duplicate both. The `evt` key per line was also left out: messages
are already fixed phrases, and `mod` gives the subsystem.

The first real device will fail somewhere in ALSA or GPIO, and today that produces an "oops"
and zero log lines: `deviceController.ts:423` `startRecording(...).catch(() => null)`, plus
send, playback and delete failures; `routes.ts` has no logger at all; three idioms of error
handling with no stated policy (33 bare `catch {}`, 9 `.catch(() => undefined)`).

- `onFault(kind, index, err)` on `DeviceControllerOptions` — structurally typed like
  `StatsRecorder`, so core stays pure — logged at warn by the composition root. Logger in
  `RoutesContext`.
- A three-rule error policy in `architecture.md`: **core returns results; adapters throw typed
  errors; a swallow always logs with a stable event name.**
- `log.child({ mod })` per subsystem and an `evt` key, so logs are countable, not prose.
- PII: `whatsapp-bridge.ts:64,171` log full JIDs at info, and the diagnostics bundle ships the
  journal verbatim. Mask numbers (`+49•••4567`) or pino `redact`; pin Baileys' logger to
  `warn` unless a separate variable raises it.
- An in-memory ring buffer of recent warn/error events at `GET /api/system/events` (admin),
  shown on the health card — the only post-mortem a parent can reach without ssh.
- `wa:heartbeat` from the bridge carrying Baileys' last activity; stale ⇒ WhatsApp error state.

### 2C. A thin application layer; routes become parse → call → map

Routes run multi-step workflows themselves (`/wifi/join`, `/factory-reset`, `/onboard`) against
a 17-closure `RoutesContext`. Extract:

- `SetupService` — onboard, join Wi-Fi, forget Wi-Fi, factory reset.
- `PairingService` — link by QR / phone code, unlink, groups.
- `DeviceAdminService` — power, silent, stats reset, test speaker.

Split `routes.ts` (637 lines) into one router per resource, each taking only its service. Every
request body validated by a small Zod schema at the edge, reusing the existing `issues` shape;
a final JSON error handler that returns 500 (not 400 with the raw `error.message` and a file
path, `routes.ts:191,308`) for anything that is not a validation error.

### 2D. Core: one audio arbiter, explicit state, no I/O

- **Audio arbiter.** Cues, capture and playback go through one owner that knows whether the box
  is `idle | listening | capturing | finishing-send`. `shouldPlayCue` is decided at 9 call
  sites today, which is why 0.1 had nowhere to be enforced.
- **`ButtonInterpreter` as one explicit state value.** `ActivePress` carries four booleans
  (`confirmed/blocked/withheld/swallowed`, 16 combinations, ~5 legal) across two Maps, a Set and
  a timer. The staged lockout already *is* a single-owner model; make the code say so:

  ```ts
  type Owner =
    | { kind: 'idle' }
    | { kind: 'press'; index: ButtonIndex; startedAt: number;
        mic: 'waiting' | 'open' | 'withheld' | 'refused'; timers: PressTimers }
    | { kind: 'window'; index: ButtonIndex; startedAt: number; releasedAt: number; timers: WindowTimers }
    | { kind: 'chord'; timer: Timer };
  ```

  Every input a `switch` ending in an `assertNever`. `#isLockedOut` / `#canJoinChord` collapse
  to a `kind` check; the watchdog of 0.10 is one field on `press`.
- **Split `DeviceController` (602 lines, seven jobs):** `CaptureSession` (begin/commit/discard),
  `QuietHoursScheduler`, the arbiter above; pass a `DeviceConfig` **snapshot**, not the
  `ConfigManager` (it mixes both today, `:385,576`).
- **Remove the `rm` from core** (`deviceController.ts:1,464,544`) behind a `NoteStore.delete`
  port. That also lets `deviceController.test.ts` run fully on fake timers, dropping the
  `mkdtemp` + 500-iteration `waitFor`. Then make the two docs agree — the root CLAUDE.md says
  core does no I/O, `architecture.md:132` says the controller is where I/O is allowed.
- `audio/queueManager.ts` is pure sequencing and belongs in `core/`.

### 2E. HAL: ports, a shared pipeline, a contract suite

- Split `hal/types.ts` into `ButtonInput`, `LampOutput`, `AudioOut`, `AudioIn`, `Lifecycle`, with
  `type Hal = ButtonInput & LampOutput & AudioOut & AudioIn & Lifecycle` so drivers stay one
  object. Consumers declare the narrow port (animator ← `LampOutput`, queue ← `AudioOut`).
- Move encode/decode/duration/filter defaults into `audio/pipeline.ts`; the GPIO and simulator
  drivers each duplicate them and have already drifted.
- `describeHalContract(makeDriver)` run against mock, simulator and GPIO-with-fake-children:

## Phase 4 — deployment model (M)

- **Atomic upgrades with rollback.** `/opt/bloopbox/releases/<ver>-<sha>`, `ln -sfn` + `mv -T`
  swap of `current`, keep the previous, auto-revert if the units are not active 60 s after the
  swap. Today `install.sh:319-324` deletes `.old` first and a power cut between two `mv`s leaves
  no app. Pair with the known `/data`-partition + read-only-root item.
- **Release integrity:** `actions/attest-build-provenance` (verify with `gh attestation
  verify`) or a minisign key baked into the image and checked by `install.sh`.
- **One hardening drop-in** for all four units: `SystemCallFilter=@system-service`,
  `SystemCallArchitectures=native`, `RestrictAddressFamilies`, `ProtectKernelModules/Logs`,
  `ProtectClock`, `ProtectHostname`, `RestrictNamespaces`, `LockPersonality`, `UMask=0077`,
  `ProtectProc=invisible`; `DevicePolicy=closed` + `DeviceAllow` for GPIO/ALSA on the hardware
  unit; `CapabilityBoundingSet=CAP_NET_ADMIN` on the root agent. **Not**
  `MemoryDenyWriteExecute` (breaks V8's JIT). Verify `rfkill unblock` under
  `PrivateDevices=yes` on the device.

## Deliberately not recommended

- A UI framework, ESLint, a state-machine library (XState), or supertest — each contradicts a
  decision already made for good reasons, and the plain-TS versions above are small.
- Live config reload. The restart-on-save model is simple and correct; the fixes above are about
  making the restart bounded and observable, not avoiding it.
- Touching the whitelist's rules. The review found no bypass; the changes near it (0.5, 0.12,
  wrappers) are all about what happens *around* it, and each should be read against
  `whitelist.test.ts` first.
